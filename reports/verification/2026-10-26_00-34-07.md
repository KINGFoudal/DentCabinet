## ❌ Problèmes

1. `[H]` **Sécurité : lignes rattachées à la facture ou au patient d'un autre cabinet.** Aucune contrainte ne vérifie que `invoice_id`, `quote_id` ou `patient_id` appartient au même cabinet que la ligne (`payments`, `invoice_items`, `payment_installments`, `quote_items`, `prescriptions`, `documents`, `appointments`...). Exploitation : un patient crée son propre cabinet (essai gratuit), insère un paiement « espèces » sur la facture de son dentiste ; le recalcul serveur la marque payée. Correction : clés étrangères composites `(id, cabinet_id)` ou déclencheur « même cabinet ». `supabase/migrations/20261024000000_init.sql`.
2. `[H]` **Sécurité : chemin de document non lié au cabinet.** Un admin ou secrétariat du cabinet A peut déclarer un document dont `storage_path` pointe vers un fichier du cabinet B et le lire. Correction : imposer le préfixe `{cabinet_id}/{patient_id}/` à l'écriture et vérifier le dossier dans `documents_bucket_read`.
3. `[H]` **Sécurité : redirection ouverte après connexion.** `safeNext` accepte `/\evil.com`. `src/lib/auth/validation.ts:17`. Correction : analyser avec `new URL`, même origine obligatoire.
4. `[H]` **Sécurité : `accept_invitation` contournable avec un compte sans email** (compte téléphone de l'espace patient) : la comparaison avec NULL ne lève pas d'exception. Correction : refuser si l'email est NULL ou non confirmé.
5. `[H]` **Qualité : textes non traduits** (page d'accueil, deux erreurs de l'inscription, messages bruts de Supabase, libellés d'accessibilité).
6. `[P]` **Langage : erreurs Supabase ignorées dans le paiement** (`src/lib/payments/service.ts:220-227`) : si l'enregistrement du jeton Orange Money échoue, le webhook légitime est refusé et la transaction reste « en attente » sans trace.

## ⚠️ Avertissements principaux

### Sécurité
- `[H]` Données de santé conservées sur l'appareil quand la session expire sans déconnexion explicite ; cache non lié à l'utilisateur (`auth-provider.tsx`, `cabinet-provider.tsx`).
- `[H]` Paiement « sandbox » actif par défaut hors Vercel production (`src/lib/payments/config.ts`) ; `[P]` secret de repli en dur `"nimba-sandbox"`.
- `[H]` Code de connexion (OTP) écrit dans les journaux en mode simulation (`supabase/functions/send-sms-hook/index.ts:64`).
- `[H]` Réglages d'authentification locaux faibles à ne pas pousser en production (`supabase/config.toml`).
- `[H]` Pas d'en-têtes de sécurité HTTP (CSP, HSTS, frame-ancestors).
- `[H]` Comparaisons de secrets non constantes (Edge Functions) ; `active_dentist_count` appelable pour tout cabinet ; pas de limite de débit sur `/api/payments/*`.
- `[H]` Politique `for all` (DELETE compris) sur `plans`.

### Modèles
- `[H]` Rappels : une ligne peut rester bloquée « queued » et une erreur arrête tout le lot ; troncature silencieuse au-delà de 1000 rendez-vous ; pas de délai maximal sur les appels sortants.
- `[H]` Synchronisation : boucle `push/pull` sans plafond ; classement des erreurs réseau/serveur imprécis (une erreur passagère peut annuler une modification) ; pagination par décalage pouvant sauter une ligne.
- `[H]` Suivi des paiements mobiles : annulation incomplète, fin silencieuse après délai.
- `[H]` Service worker : pas de délai réseau, caches sans limite, version figée.

### Qualité et langage
- `[H]` Filtre `cabinet_id` manquant dans `chart-tab.tsx`.
- `[H]` 12 écritures locales lancées avec `void` sans message d'erreur ; plusieurs `{ error }` Supabase ignorés côté paiement et portail.
- `[H]` Code dupliqué (`useOnline`, suivi de paiement), composants de plus de 250 lignes, dépendance Playwright sans tests e2e, README ambigu.

## ✅ Points forts vérifiés
- Typage strict, 0 erreur `tsc`, 0 erreur `eslint`, aucun `any`, 262 tests réussis.
- Aucun secret versionné ; clé service uniquement côté serveur.
- RLS sur toutes les tables, sans politique DELETE (sauf `plans`), fonctions `security definer` avec `search_path` fixe.
- Webhooks de paiement authentifiés et idempotents ; montants recalculés côté serveur.
- Boucles bornées, nettoyage des intervalles et écouteurs, rappels limités à 3 tentatives et sans double envoi.
- Écritures hors ligne centralisées dans `mutate`, traductions fr/en complètes dans les modules.

## Recommandations
1. Corriger les problèmes 1 à 4 (sécurité) et 6, et appliquer la migration en production.
2. Effacer les données locales à la fin de session ; sandbox paiement et messagerie uniquement sur demande explicite ; ne jamais journaliser l'OTP.
3. Fiabiliser l'envoi des rappels (try/catch par envoi, lignes « queued » anciennes, pagination, délais).
4. Corriger la synchronisation (classement des erreurs, plafond de boucle) et les suivis de paiement.
5. Traductions manquantes, en-têtes HTTP, refactorisations.
